### Entity errors without an index in their path are no longer dropped by the caching plugins ([PR #9986](https://github.com/apollographql/router/pull/9986))

When `preview_entity_cache` or `response_cache` reassembles an `_entities` fetch, it replaces the subgraph's error list with the errors it could match to a fetched entity. An error is matched by the index in its path — `["_entities", 0, "name"]` — so errors reported without that index were matched to nothing and silently discarded. Clients saw nulled fields with no error explaining them, or, with `supergraph.enable_result_coercion_errors` on, only a `RESPONSE_VALIDATION_FAILED` "Missing field".

Not every subgraph framework emits the index: some may resolve `_entities` without a context per list element and report `["_entities", "name"]`, so every entity-fetch error from such a subgraph would be lost whenever the response cache was enabled for it. The plain router, with caching off, has always handled these paths correctly.

Errors that cannot be tied to one fetched entity are now passed through, which produces the same client-facing response as running with the cache disabled. When the fetch went to the subgraph for a single entity, an index-less error can only be about that one, so it is attributed to it instead of being reported against every entity of the fetch — including entities served from the cache that the subgraph never saw. An error naming an entity index the reassembly never reaches — a subgraph numbering against the pre-cache representation list, or returning more entities than were asked for — has that index stripped, since it means nothing outside the subgraph's own response and would otherwise be resolved against the original representation list and blame an unrelated entity.

Because the router cannot tell which entity an index-less error from a multi-entity fetch invalidates, **no entity from that fetch is cached** — a subgraph that returns such errors alongside otherwise cacheable entities will see those entities skipped rather than stored. Only errors pointing into `_entities` have that effect: an error with no path, or with a path outside `_entities`, is passed through without touching the cache decision, so a global or unrelated error attached to every response cannot silently take a subgraph's entity caching out of service. The cache debugger reports suppressed entries as a `SUBGRAPH_ERRORS` warning with `shouldStore: false`, and `response_cache` logs the skipped batch at debug level.

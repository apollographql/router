---
title: Circuit Breaking
subtitle: Protect subgraphs and connectors from cascading failures with automatic circuit breaking
---

Circuit breaking prevents cascading failures in your distributed system by temporarily halting requests to subgraph operations or connector sources that are failing. When the router detects repeated errors, it stops sending requests to the affected target, giving the service time to recover without being overwhelmed.

The router's built-in circuit breaker supports both **subgraphs** and **Apollo Connectors**:

- For subgraphs, it operates at **per-field granularity** using type-qualified field coordinates. If a single resolver starts failing, only requests touching that field are blocked — other healthy fields on the same subgraph continue normally.
- For connectors, it operates at **per-source granularity**. Each connector source has an independent circuit.

## How it works

The circuit breaker follows a three-state model:

1. **Closed** (normal): All requests pass through. The router counts errors within a sliding time window.
2. **Open** (tripped): When the error count reaches the configured threshold, the circuit opens. Requests for the affected target are immediately rejected with a `CIRCUIT_BREAKER_OPEN` error.
3. **Half-open** (probing): After the recovery timeout elapses, the router allows a limited number of probe requests through. If a probe succeeds, the circuit closes. If it fails, the circuit reopens.

## Configuration

Circuit breaking is disabled by default. Enable it by adding `circuit_breaking` to your [YAML config file](/router/configuration/overview/#yaml-config-file):

```yaml title="router.yaml"
circuit_breaking:
  all:
    enabled: true
```

### Subgraph settings

Use `all` to set defaults for every subgraph. Use `subgraphs` to override settings for specific subgraphs:

```yaml title="router.yaml"
circuit_breaking:
  all:
    enabled: true
    error_threshold: 5
    window: 30s
    recovery_timeout: 60s
    half_open_max_requests: 1
    mode: enforce
  subgraphs:
    products:
      enabled: true
      error_threshold: 3
      window: 15s
      recovery_timeout: 30s
```

Per-subgraph settings are merged with the global defaults. Any field not specified in a subgraph override inherits from `all`.

### Connector settings

Use the `connector` section to configure circuit breaking for Apollo Connectors. Use `connector.all` to set defaults for every connector source which can be overridden per source under `connector.sources`:

```yaml title="router.yaml"
circuit_breaking:
  connector:
    all:
      enabled: true
      error_threshold: 3
      window: 30s
      recovery_timeout: 60s
      mode: enforce
    sources:
      "connectors.jsonPlaceholder":
        error_threshold: 10
```

Source names use the format `"subgraph_name.source_name"` (for example, `"connectors.jsonPlaceholder"`). Per-source settings are merged with `connector.all` the same way subgraph settings merge with `all`.

Subgraph and connector configurations are independent — the top-level `all` setting only applies to subgraphs, not connectors.

### Options reference

| Option | Default | Description |
|---|---|---|
| `enabled` | `false` | Whether circuit breaking is active. |
| `error_threshold` | `5` | Number of errors within the sliding window required to trip the circuit. |
| `window` | `30s` | Duration of the sliding error-counting window. If the window expires without reaching the threshold, the error count resets. |
| `recovery_timeout` | `60s` | How long the circuit stays open before transitioning to half-open and allowing probe requests. |
| `half_open_max_requests` | `1` | Maximum concurrent probe requests allowed while the circuit is half-open. |
| `mode` | `enforce` | Either `enforce` (reject requests when open) or `measure` (log state transitions but never reject). |

### Measure mode

Use `measure` mode to observe circuit breaker behavior in production before enforcing it. In measure mode the router tracks errors, counts state transitions, and emits metrics, but never rejects requests:

```yaml title="router.yaml"
circuit_breaking:
  all:
    enabled: true
    mode: measure
  connector:
    all:
      enabled: true
      mode: measure
```

## Granularity

### Subgraphs

The circuit breaker keys subgraph state by **type-qualified field coordinates** (for example, `Product.inventory`). This means:

- Two different client queries that touch the same field on the same subgraph share the same circuit.
- Two different fields on the same subgraph have independent circuits.

This prevents a single failing resolver from blocking all traffic to an otherwise healthy subgraph.

### Connectors

The circuit breaker keys connector state by **source name** (for example, `connectors.jsonPlaceholder`). Each connector source has its own independent circuit. Connector circuits are also fully independent from subgraph circuits.

## Error responses

When the circuit is open and mode is `enforce`, the router returns a GraphQL error with the `CIRCUIT_BREAKER_OPEN` code:

```json
{
  "errors": [
    {
      "message": "Circuit breaker is open",
      "extensions": {
        "code": "CIRCUIT_BREAKER_OPEN"
      }
    }
  ]
}
```

The error message is intentionally generic and does not expose internal subgraph or connector names. Detailed information (subgraph name, field coordinate, or connector source) is logged server-side for debugging.

## Metrics

The router emits the following metrics for observability:

| Metric | Description | Attributes |
|---|---|---|
| `apollo.router.circuit_breaker.state_change` | Counter incremented on every state transition (closed → open, open → half-open, etc.) | `subgraph.name` or `connector.source.name`, `circuit_breaker.from_state`, `circuit_breaker.to_state` |
| `apollo.router.circuit_breaker.rejected` | Counter incremented each time a request is rejected by an open circuit. | `subgraph.name` or `connector.source.name` |

## External circuit breaking

In addition to the router's built-in circuit breaker, you can use external infrastructure for circuit breaking.

### Service meshes and proxies

Service meshes like [Istio](https://istio.io/) and proxies such as [Envoy](https://www.envoyproxy.io/) and [NGINX](https://www.nginx.com/) provide circuit breaking at the network level. These tools monitor health, error rates, and latency to halt or reroute traffic to failing services.

Service mesh circuit breaking is typically not GraphQL-aware and treats entire subgraphs atomically, lacking per-operation granularity.

### Application-level circuit breakers

You can also wrap data sources or resolvers with circuit breaker logic using libraries like [`opossum`](https://github.com/nodeshift/opossum) (Node.js) or [`resilience4j`](https://github.com/resilience4j/resilience4j) (Java) in your subgraph services. This approach enables per-resolver or per-backend API circuit breaking but requires coordination across services.
